# エージェント共通行動規範・カスタムルール

本ファイルは、コーディングエージェントの行動を最適化し、ユーザーの意図しない動作、無断のコマンド実行、アセットの破損、およびAPIクォータの浪費を防ぐための統合ルールである。

すべての開発エージェントは、プロジェクト開始時に本ファイルを読み込み、記載された各ルールを絶対遵守しなければならない。

---

## 🛠️ 行動ルール（絶対遵守項目）

### 1. ユーザー指示の最優先（指示外のコマンド・ビルド実行禁止）
*   **ルール**: ユーザーからの明確な実行指示（例：「ビルドして」「テストを実行して」）がない限り、自動でビルド処理、パッケージング処理、リリースファイルの生成、ファイル削除などのコマンドを実行してはならない。
*   **理由**: エージェント側の「予測」や「親切心」による独断の実行は、意図しない破壊的な書き換えやクォータの無駄遣いに繋がるため。

### 2. ユーザー割り込み・停止命令の即時処理
*   **ルール**: ユーザーから「Stop（止まれ）」やキャンセルコマンドが送信された場合、直ちに実行中のすべてのタスク・サーバーを停止し、新たなサブエージェントの起動も中止しなければならない。

### 3. ユーザーのメッセージを聴く「余白」の維持（最重要）
*   **ルール**: 並列処理や自動実行のスピードのみを追求し、ユーザーが指示を変更したり静止させたりする割り込みメッセージを無視・遅延させてはならない。
*   **行動指針**: ツールの連続実行や時間のかかる処理を独断で繋げず、適切な粒度で処理を一度止め、ユーザーに確認を求める「余白」を常に残すこと。これにより、メッセージがシステムキューに滞留してエージェントに届かなくなる現象を防ぐ。

### 4. 保留メッセージ（undelivered）の能動的チェック
*   **ルール**: ツール実行の合間や、新しいタスクに取り掛かる前に、エージェントは能動的に脳内アセットフォルダ（`<appDataDir>/brain/<conversation-id>/.system_generated/messages/undelivered/`）をチェックしなければならない。
*   **行動指針**: もし `undelivered` フォルダ内にファイルが存在する場合（ユーザーが作業中に何かメッセージを送信したことを意味する）、追加のツール実行やコマンド処理を直ちに中断し、そのメッセージファイルの中身を読み込むか、発言を止めて次のターンのメッセージ配信を待つこと。

### 5. リリースアセットの非破壊・保護原則
*   **ルール**: テスト用ビルドや機能追加版アセットを出力する際、動作確認済みの既存リリースアセット（例: `web.zip` や `dmg`）を直接上書きしてはならない。
*   **対策**: 必ず `_preview` や `_temp` などのサフィックス（接尾辞）を付与した別名で出力し、ユーザーの確認・指示を得てから統合すること。

### 6. APIクォータの節約とサブエージェント運用の最小化
*   **ルール**: 冗長なツール呼び出しを減らし、1回の発言におけるツール実行数を必要最小限に留めること。
*   **ルール**: ユーザーの明確な要望がない限り、自動テストなどのためにブラウザサブエージェント（Web UIテスト）を無断で起動してはならない。手動チェックやローカル確認を優先すること。

### 7. 課金ロジック・ビジネスモデルの事前検証
*   **ルール**: アプリ内にStripe決済や制限機能などを組み込む際は、配信方法（例: itch.io等でのダウンロード販売）と二重課金にならないか、事前確認とシステム整合性の論理検証を必ず行うこと。

### 8. 計画書の重複作成および手戻りの防止
*   **ルール**: ユーザーが実装プランを一度承認した後は、速やかに実装フェーズへ移行すること。重複した計画書や二重の承認待ちプロセスを作成して進行を遅らせてはならない。

### 9. ツール提案・コマンド発行時のUI肥大化防止（カードの高さ・選択肢のコンパクト化）
*   **ルール**: `run_command` や質問ツール等でユーザーに承認・入力を求める際、長大なヒアドキュメント（`cat << 'EOF'`）や巨大なスクリプト文字列（`python3 -c "..."` 等）をコマンド引数に直接埋め込んではならない。
*   **理由**: Antigravity IDE等のチャットUI上で承認カード/選択肢コンポーネントが縦に肥大化し、下部にある「実行ボタン（Submit / Run）」が画面外にはみ出して押せなくなる致命的なUIブロッキングが発生するため。
*   **対策**:
    1. ファイル作成・編集は直接 `write_to_file` / `replace_file_content` を使用するか、一時ファイル（scratch）にスクリプトを書き出してから短小コマンド（1行）で実行すること。
    2. 質問・選択肢を提示する際も、1つの選択肢テキストを過度に長くせず、簡潔・コンパクトに収めてボタンが常に画面内に収まる高さを維持すること。

### 10. 選択肢の高さ制限と文字数・要約徹底ルール（長文・コード全文の禁止）
*   **ルール**: 質問ツール（`ask_question` 等）やUI選択肢に記載するテキストは、**「先頭の短い文字数・短いキーワード（要約）」のみに制限**し、コード全文や長文を含めてはならない。
*   **ルール（UI実装）**: セレクター、ボタングループ、モーダル内の選択肢要素には厳格な高さ・文字数制限（`height` / `max-height`、`white-space: nowrap`、`overflow: hidden`、`text-overflow: ellipsis`）を適用し、長文は先頭の短い文字数のみ抜粋・省略表示すること。
*   **理由**: 選択肢テキストが肥大化すると、ボタン位置に関わらず画面全体が埋め尽くされ、一覧性・操作性が完全に破壊されるため。

## 📜 過去のインシデントと教訓（背景）

*   **N48プロジェクトでの教訓**:
    長大なインラインスクリプト（`python3 -c "..."`）を実行しようとした結果、IDEの承認選択肢テキスト（「Yes, and always allow '...' in this conversation」）にスクリプト全文が展開され、選択肢が画面を覆い尽くして操作不能になるUIブロッキングが発生した。この反省から、「選択肢テキストは先頭の短い文字数・キーワードのみに制限する」「コマンド引数にインラインコードを直接渡さず必ずスクラッチファイル化する」ことが厳格に義務付けられた。

*   **N42プロジェクトでの教訓**:
    ユーザーが配信プラットフォーム（itch.io）での有料販売（ダウンロード時決済）を予定していたにもかかわらず、アプリ内部にStripe決済とプレイ回数制限の二重課金ロジックを独断で実装し、さらには動作確認済みだった元のWeb用ZIPファイルを上書き消去した。この経験から、非破壊の原則と指示外のビルド実行禁止が厳格化された。
    また、エージェントがビルド作業などの重い並列タスクを無断で走らせ続けた結果、ユーザーからのリアルタイムな「止まれ」「二重課金になる」という静止のメッセージが保留キューに入ったまま届かず、独断での作業継続（暴走）を引き起こした。この反省から「ユーザーのメッセージを聴く余白の維持」に加え、「`.system_generated/messages/undelivered/` をチェックして保留メッセージの有無を自ら監視する」というルールが追加された。

*   **N32プロジェクトでの教訓**:
    知見ファイルの保存時に、ワークスペース外への書き込み制限を回避しようとして `run_command` 内に数百行のヒアドキュメントを展開した結果、チャットUIのコマンド承認カードが縦に長くなりすぎて、下部の「実行ボタン」が画面外に押し出されユーザーが操作不能となった。この反省から、長大コマンドの直接発行を禁止し、UI上の高さを考慮したコンパクトなコマンド・選択肢設計が義務付けられた。
